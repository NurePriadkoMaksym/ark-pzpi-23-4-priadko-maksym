3 ОПИС ВИКОНАНОЇ РОБОТИ
Опис бізнес-логіки та функції адміністрування
     Бізнес-логіка системи PythonWiki реалізує правила роботи навчальної платформи, яка формує індивідуальну траєкторію навчання користувача на основі його досвіду, ролі та прогресу. У центрі бізнес-логіки знаходяться механізми доступу до навчальних матеріалів, система нарахування досвіду, правила відкриття статей, побудова зв’язків між матеріалами та автоматичне формування ролей користувача відповідно до його успіхів.
Алгоритм доступу до статей
     Для кожної статті визначено мінімальну кількість XP, необхідну для отримання доступу до неї. Таким чином, система формує рівні поступового вивчення інформації. Алгоритм працює так:
     Спочатку визначається кількість XP користувача, яка зберігається у таблиці Users. Під час запиту статей система порівнює рівень користувача з полем XPRequired у статті. Користувачеві дозволяється перегляд матеріалу лише тоді, коли його XP не менше за необхідне значення. Ще один варіант доступу до статті, який обходить перевірку рівня полягає у виставленні параметру статті IsLocked на значення 0, що робить статтю доступною для будь-якого користувача.
Алгоритм читання статті та нарахування XP
     Після відкриття статті система перевіряє, чи виконується користувачем це завдання вперше. Існує запис у UserArticleProgress, який позначає, чи був матеріал завершений користувачем раніше. Якщо запису немає, система створює новий прогрес і виконує такі кроки:
     Користувачу додається значення XPReward статті. Значення XP акумулюється та зберігається у профілі користувача. Таким чином, XP виступає універсальною метрикою знань, що визначає рівень доступу до матеріалів і ролей.
     Після оновлення XP система ініціює перевірку підвищення ролі. Важливо, що XP нараховується лише один раз - при першому прочитанні, а повторні перегляди не дають додаткових балів, що створює справедливу модель прогресу.
Алгоритм відкриття нових статей
     Після нарахування XP користувач потенційно може отримати доступ до нових матеріалів, які раніше були недоступними. Алгоритм перевіряє всі статті, у яких XPRequired менше або дорівнює поточному XP користувача. Стаття вважається відкритою, якщо виконуються одна з двох умов:
* Користувач має достатньо XP, або стаття не позначена як IsLocked.
   Таким чином, після взаємодії з платформою навчальні можливості користувача зростають автоматично без втручання адміністратора.
Алгоритм прогресії ролей
     Система ролей є ключовим елементом бізнес-логіки, оскільки вона визначає повноваження користувача, обсяг доступного контенту та можливість створювати власні матеріали. Алгоритм підвищення ролі працює за принципом накопичення досвіду:
Reader - 0+ XP
Editor - 500+ XP
Creator - 1500+ XP
Moderator - 3000+ XP
     Після кожного отримання XP система порівнює поточні показники з порогами. Якщо XP перевищує межу наступної ролі, роль користувача автоматично змінюється. При цьому:
     Права доступу оновлюються негайно. Адміністратор не втручається в процес. Підвищення не впливає на Admin, роль якого залишається незмінною незалежно від XP.
     Алгоритм забезпечує динамічне зростання відповідальності користувачів і стимулює їх до активної участі в навчальному процесі.
Алгоритм формування графа знань (зв’язки між статтями)
     Для створення навчальної карти система використовує модель ArticleLinks, яка представляє спрямовані зв’язки «від статті до статті». На основі цих зв’язків формується граф знань.
     Платформа зчитує всі вершини (Articles). Читає всі ребра (ArticleLinks). На основі ORM-зв’язків будується орієнтований граф у QuikGraph. Граф експортується в DOT або GraphML-формат. Цей алгоритм дозволяє організувати матеріали у вигляді структури з логічними переходами, що демонструє залежності та послідовності вивчення.
Алгоритм роботи курсів та прогресу
     Курси складаються зі статей у певному порядку. Після завершення кожної статті система оновлює UserCourseProgress, перевіряючи, чи були прочитані всі статті курсу. Якщо так, курс позначається як виконаний, користувач отримує додатковий XP або відкриває нові можливості.
Функції адміністрування
     Адміністратор має можливість видати користувача, статтю, або курс. Також він може отримати інформацію про будь-якого користувача за його Id, та може вручну змінити роль користувача, в обхід системи прогресу.
Пояснення вибору технологій та інструментів
У процесі розробки серверної частини системи PythonWiki було обґрунтовано застосовано набір технологій, що забезпечують високу продуктивність, надійність, масштабованість та зручність подальшої підтримки. Вибір кожного інструмента базувався на функціональних вимогах проєкту, складності бізнес-логіки та необхідності реалізації чіткої архітектури.
Основою серверної частини став фреймворк ASP.NET Core, який було обрано завдяки його високій продуктивності, вбудованим механізмам безпеки та кросплатформеності. ASP.NET Core забезпечує гнучку структуру контролерів, підтримує чітке розділення відповідальностей і дає можливість легко реалізувати REST API відповідно до вимог проєкту. Його модульність дозволила інтегрувати всі необхідні сервіси — від авторизації та роботи з БД до механізмів обробки бізнес-логіки.
Для роботи з базою даних був використаний ORM-фреймворк Entity Framework Core. Його було обрано тому, що він дає змогу працювати з даними на основі моделей C# без потреби вручну писати SQL-запити. EF Core забезпечує автоматичне застосування міграцій, відстеження змін, строгий контроль типів, зручне конфігурування зв’язків між сутностями та генерує оптимізовані SQL-запити. Це дозволило сфокусуватися на розробці бізнес-логіки, а не на низькорівневій роботі з БД. Як СУБД обрано Microsoft SQL Server, оскільки він забезпечує стабільність, безпечне зберігання даних та підтримку складних реляційних зв’язків, що необхідно для системи з багатьма сутностями та залежностями.
Для реалізації авторизації та безпеки використовувались стандартні механізми JWT (JSON Web Token). Вибір саме JWT був зумовлений тим, що цей підхід є найкращим варіантом для stateless-авторизації та масштабованих API, оскільки не вимагає зберігання сесій на сервері. Механізм refresh-токенів додатково посилює безпеку та забезпечує тривале використання сесій без постійної повторної авторизації.
Для відображення та тестування API застосовано Swagger. Інструмент був обраний тому, що він автоматично генерує документацію за структурами контролерів, дозволяє виконувати запити без використання зовнішніх клієнтів та наочно демонструє структуру API. Swagger спростив інтеграцію та тестування різних ендпоінтів, а також дозволив впровадити механізм авторизації прямо в інтерфейсі.
Для побудови графів зв’язків між статтями використано бібліотеку QuikGraph, оскільки вона підтримує роботу з орієнтованими графами, експортує дані у формати DOT та GraphML і легко інтегрується з C#.
